## 1. Qué pedía el RFC y qué se ha hecho

El RFC pedía resolver C-015 **sin** modificar la declaración histórica ni emitir certificaciones
retroactivas. La declaración phase 1 existe, está sellada y contiene `generator_code_commit` a cero
porque el generador no existía cuando se congeló. Editarla ahora sería exactamente la corrección
retroactiva que RFC-050 prohíbe.

Se ha emitido una **declaración sucesora** que:

1. conserva la declaración original byte a byte (ACC-01);
2. la referencia por ruta, `sha256` y blob de Git, sin modificarla;
3. nombra el generador por su commit completo (`fc036d9…`) y por el `sha256` del blob que ese commit
   contiene (ACC-03, ACC-04);
4. fija un instante de vigencia **anterior** a la apertura de la ventana y exige que cada barra haya
   sido capturada después de ese instante (ACC-05, ACC-06);
5. no cambia ventana, activos, costes, umbrales ni criterios de aceptación: la única diferencia por
   entrada es `generator_code_commit`.

## 2. ¿Admite la gobernanza existente una declaración sucesora?

Es la pregunta que §5.2 obliga a responder antes de usarla, y la respuesta está en el código, no en
una declaración de intenciones:

- `prereg_gate.evaluate()` recibe el registro de datasets **por parámetro**
  (`registry_path: str = "config/dataset_registry.json"`), no por una ruta fija para EXP-004A.
  Cualquier registro con el mismo esquema puede ser evaluado.
- La declaración sucesora **reutiliza el esquema de entradas de phase 1 sin añadir un dialecto**: los
  cuatro `entries` son los mismos objetos, campo por campo, salvo `generator_code_commit`. Las
  claves nuevas (`declaration_id`, `supersedes`, `generator`, `capture_window`, `effective_from_utc`,
  `governance_status`) viven en el nivel superior del documento, donde el gate no interpreta nada y
  por tanto no puede confundirlas con datos del experimento.
- No se ha añadido, quitado ni relajado **ninguna** regla de `prereg_gate`. No se ha creado una
  identidad experimental nueva, porque no era necesario: la sustitución es una sustitución de
  registro, no del experimento.

**Lectura registrada:** la sucesión es admisible *como registro* con el contrato existente, y por eso
este paquete no modifica el gate. Lo que el gate **no** hace es verificar la sucesión; esa
comprobación se implementa como preflight y como control del verificador
(`ORIGINAL_DECLARATION_UNCHANGED`, `SUPERSEDES_LINK`, `V-PROV-05`, `V-PROV-06`). Si un WP futuro
quiere que el propio gate la exija, deberá enmendarlo de forma explícita; aquí no se ha hecho.

### 3.1 Flujo de ejecución

```
DECLARATION → GOVERNANCE VALIDATION → GENERATOR VALIDATION → CAPTURE → RAW EVIDENCE
            → ADMISSION → INDEPENDENT VERIFICATION → RUN REPORT
```

Cada transición es un código de salida distinto y no intercambiable:

| Situación | Exit | Efecto |
| --- | --- | --- |
| Declaración ausente / no autorizada / commit inválido / código distinto | `2` | BLOCK, no se escribe nada |
| Ventana vacía | `3` | REJECT |
| Fuente ausente o corrupta | `4` | REJECT |
| Barra capturada antes de la vigencia o fuera de ventana | `5` | NOT_ELIGIBLE |
| Slice correcto y elegible | `0` | dataset + manifiesto con bloque `provenance` |

### 3.2 Registro de procedencia

Cada manifiesto de captura lleva ahora un bloque `provenance` con: `declaration_id`, ruta y `sha256`
de la declaración, commit que la contiene, `generator.commit` y `sha256` del blob declarado,
`supersedes.sha256`, ventana temporal, `basis = GIT_ANCESTRY_PLUS_INGEST_CLOCK` y
`external_timestamp = UNAVAILABLE`. El registro **no** afirma una notarización que este repositorio no
tiene.

### 3.3 Elegibilidad temporal

La elegibilidad se decide contra `fetched_at_ms` de cada barra — el reloj que el store escribe en el
momento de la ingesta y que no forma parte de ningún documento editable después. Regla:

```
bar.fetched_at_ms >= declaration.effective_from_utc
bar.open_ms ∈ [capture_window.start_utc, capture_window.end_utc)
```

Una barra que no cumple la primera condición se conserva en el store pero **no** puede entrar en un
dataset elegible: el extractor sale con 5 y no escribe fichero.

## 5. Lo que este RFC no puede declarar

1. **No hay validación prospectiva.** La ventana abre mañana; no existe ninguna jornada observada bajo
   la nueva declaración. `PAPER_VALIDATION = NOT_PASS`.
2. **C-013 sigue `TIME_PROOF_WEAK`.** La cronología se apoya en ascendencia de Git y en el reloj de
   ingesta. Ninguno de los dos es un sello de tiempo de confianza; el sistema lo dice en cada registro
   (`external_timestamp = UNAVAILABLE`) en lugar de heredar una autoridad que no tiene.
3. **C-016 no se toca.** Sigue `UNREACHABLE_UNDER_DECLARED_COST_MODEL`; 20 bps frente a un suelo de
   comisión medido de 20.001191 bps no se alcanza moviendo el umbral.
4. **No hay certificación ni promoción.** El verificador emite un veredicto técnico; el control de
   aceptación y la decisión de promoción siguen siendo de otro rol y siguen bloqueados.

## 6. Rollback

Si la declaración sucesora resultara defectuosa: se mantiene intacta la original, se invalida la
sucesora (`governance_status` a un valor no autorizado, nunca borrándola), se conservan preflight,
verificación y manifiesto, el extractor sigue rechazando `st6:tape` y toda captura sin declaración
válida, y la certificación permanece bloqueada. No se borra evidencia para simplificar el rollback.

## 7. Siguiente puerta

No es ampliar arquitectura. Es comprobar que la captura prospectiva funciona durante su ventana,
medir la calidad de los datos y decidir si existe una hipótesis económicamente viable después de
costes. Un PASS técnico de captura no es una afirmación de rentabilidad.
