Two honesty notes the phase insists on:

* **Recovery is not WebSocket.** The 15,969 restored rows carry
  `transport = rest_backfill` and are excluded from the latency distribution. A
  REST-recovered print is real market data observed later, not a WebSocket
  event, and it is never presented as one.
* **An id step is not always an event.** Only `agg_trade` ids name discrete
  events (0 lost events implied by id steps); for `depth_diff` an id step is a
  position in a sequence, so the affected book was invalidated and resnapshotted
  instead of being asked to account for a count of missing updates
  (`id_steps_that_are_a_sequence_span_only = 159,109,856`). 63.1 min is far too
  short to run M-03/M-07 admission, and that admission was **not** run.

## 6. Cost, streaming, and the closed memory defect

**The collector's own cost** (59 samples across the run): CPU 2832.406 s for
3783.42 s wall = **74.9 % of one core**; memory peak **281.56 MB**, and the final
sample *is* the maximum; network 1,293,448,253 B = 1.231 GB/h; disk written
376,480,457 B.

**The analysis side streams, and it is measured.** The original P1 was that every
analysis path materialised the dataset, so describing a forward hour cost tens of
gigabytes. `docs/FORWARD_DATA_STREAMING_MEMORY.json` samples RSS every 0.25 s
around each path over the real 5,481,951 rows: replay +20.0 MB, aggregation
+42.6 MB, quality +26.2 MB, daily +18.9 MB, verifier +24.9 MB. Worst growth
**42.6 MB** against a materialised equivalent of 109,660.9 MB (109.7 GB) ⇒ ratio
0.000389, `bounded = true`. Memory is a function of streams and intervals, not of
row count.

**The independent book check was wrong and is fixed.** The verifier graded *every*
persisted checkpoint against a rebuild from a live chain, including the states
the collector itself declared `INVALID`/`RECOVERING` and refused to feed features
from — so a correct capture failed its own verification. Those checkpoints are now
classified and traced (window, difference examples, fresh-snapshot-after) instead
of graded; coherent `HEALTHY`/`STALE` checkpoints must still match exactly, no
`HEALTHY` claim may sit on a broken chain, and every checkpoint must be accounted
for. On this capture: 708 checkpoints, 697 matched, 14 unverifiable because the
*verifier's* chain was broken, 1 declared unusable (perp SOLUSDT) and followed by
a fresh snapshot, **0 mismatches**, `ok = true` for all six books.

## 7. Defects

**FOUND → FIXED (4)**

1. **Analysis paths materialised the whole capture** (RSS grew with row count;
   the reported symptom was +9.7 GB). Fixed by making replay/aggregation/quality/
   daily/verifier stream; locked by
   `test_row_streaming_matches_a_materialised_load` and
   `test_the_quality_report_is_produced_from_one_streaming_pass`, and proven by
   §6. The report writer also stopped rebuilding a section a caller had already
   built (two extra full scans per report).
2. **The replay trade-chain invariant fired on legitimate REST recovery**
   (`repaired aggTrade id N is newer than the live stream (M)`: 15,969 repaired
   rows, 50 violations). The rule compared *write order* against the highest live
   id seen so far. It now verifies in **id space** — idempotent coverage,
   duplicate-free contiguity, repairs bounded by the live head — while a genuine
   live regression is still a violation. Re-run: 0 violations, offline replay
   green.
3. **The verifier's book check graded checkpoints the collector itself declared
   unusable** (see §6). Fixed by classification + tracing; re-run: 0 mismatches.
4. **The verifier could not see two of the phase's claims.** It now checks the
   writer-equivalence sidecar and the overclaim/final-status rule, so
   `CAPTURE_CODE_EQUIVALENT` and "no strategy outcome claimed" are machine-checked
   instead of asserted.

**P0 OPEN: 0.**

**P1 OPEN: 1 — writer state that grows with the capture.**

`StreamStats.network_delays` (`src/trading_bot/research/forward/storage.py`) is a
`list[int]` appended once per event that carries a network delay and **never
read**: no `as_dict()`, no manifest field, no report touches it. On this run
3,805,824 of 5,481,951 rows carried a delay, so the list grew by ~3.8 M entries in
63 minutes; the writer's sampling ended the capture at its maximum memory
(281.56 MB final == 281.56 MB max), the signature of monotonic per-event growth.
A controlled tracemalloc measurement of the append alone puts the retained cost at
≥ 8.1 B/event ⇒ **≥ 44.5 MB/h ≈ ≥ 1.07 GB/day floor** at this event rate.

It is **not** fixed here, and that is a deliberate trade: `storage.py` is a
`WRITER_PATHS` member, so editing `StreamStats` would break
`CAPTURE_CODE_EQUIVALENT`, and the certified hour cannot be re-run to restore it.
The fix (bounded histogram, or delete the field) belongs in the next
collection-generation commit with a short certification capture. It does not
affect the validity of the hour: the data is on disk and verifies; only the
process's long-run footprint is affected — and it is the **second** blocker to
continuous collection, after disk.

## 9. Disk guard and clean stop

The guard was exercised in a throwaway root; the real volume was never filled.
Unbounded-duration variant (`--max-total-bytes 200000`): trip → intake halted →
writer flushed → segment sealed → manifest finalised → exit 0. Bounded variant
(`--duration 90`): trip at 275,897 B vs a 200,000 B budget while the process
stayed alive, and the sockets stopped writing **26 ms** after the trip instant.
The recorded recommendation is to run the continuous invocation **without**
`--duration`, because there is no reason to keep a process alive after its own
guard has fired.

The official capture itself ended on its duration, **not** on the guard
(`stopped_on_disk_budget = false`), with its manifest finalised and 0 partial
tails — a clean stop.
