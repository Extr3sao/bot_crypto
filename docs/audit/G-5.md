# G-5 — Paper runtime end to end

**Estado:** CLOSED (scoped) · `LIVE_NO_GO` maintained · `PRODUCTION_READY = false`  
**Implementación:** `05b361f7bd26a4fb9d470d9ba5c68d7f967846c9`  
**Base medida antes de G-5:** `0bc8a926` (cierre de G-4)  
**Predecesores:** G-1, G-2, G-3, G-4, P0, RFC-TAP-EXEC-SEC-002

## 1. Objetivo

Demostrar, con ejecución y no con documentación, que el runtime paper del
repositorio completa el recorrido:

```text
datos → contexto PIT → router → señal → risk → HotStopGate
      → PaperBroker → contabilidad → estado durable → reconciliación
```

sin credenciales, sin clientes de exchange y sin ninguna orden real.

## 2. Qué se encontró

1. El motor canónico ejecutable es `PaperCycleEngine`, compuesto por
   `scripts/start_paper_trading.py::build_cycle_engine` y conducido por
   `PaperOrchestrator → PaperSessionRunner`.
2. `trading-bot run --demo` y `trading-bot run --mode paper --auto-trade`
   **no** son ese motor: construyen el scanner sintético (`market_data.fake`) y
   no crean broker, estado ni orden. El flag `--auto-trade` no se aplica.
   Antes de G-5 el texto de éxito no lo decía de forma inequívoca.
3. `PaperSessionRunner` aceptaba un `now_fn`, pero las condiciones defensivas
   (`spread`, `ATR`, latencia y fin de semana) leían el reloj de pared. En un
   domingo, un replay determinista con reloj fijado en miércoles quedaba
   bloqueado por `weekend_trading` antes de llegar a riesgo o al stop. Eso hacía
   imposible distinguir «el stop bloqueó» de «el calendario bloqueó».
4. El ledger de producción `config/strategy_admission.json` no admite ninguna
   estrategia (`paper-executable on 5m: NONE`). Por tanto el comando de
   producción ejecuta el ciclo pero termina en `NO_TRADE`; no se puede exigir
   una operación con ese ledger sin saltarse la admisión.

## 3. Requisitos

### REQ-G5-01 — Rutas honestas

Toda ruta CLI que solo ejecute el scanner sintético debe identificarse como
tal (`paper_cycle=NOT_RUN`, `broker=NOT_CONSTRUCTED`, `state=NOT_WRITTEN`) y no
debe presentar `--auto-trade` como aplicado. El comportamiento y el código de
salida de G-4 se conservan.

### REQ-G5-02 — Un comando ejecuta el ciclo real

Debe existir un comando documentado que componga el motor real, el
`RiskManager`, el `HotStopGate`, el `PaperBroker`, el estado durable y el
reconciler. El comando de producción es
`scripts/start_paper_trading.py`; el comando de evidencia controlada es
`scripts/audit/g5_paper_e2e.py`.

### REQ-G5-03 — Reloj único en la decisión

Las condiciones defensivas deben usar el mismo `now_fn` que el resto de la
sesión. El valor por defecto sigue siendo el reloj de pared; el control de
tiempo es un seam de test, no un cambio de política.

### REQ-G5-04 — Cobertura de escenarios

La evidencia debe incluir, como mínimo:

- `TRADE`: señal, riesgo aprobado, orden paper, posición y estado durable;
- `RESTART`: nuevas instancias de broker/engine/reconciler sobre el mismo
  fichero, `RECOVERED`, cero reaperturas y cierre reconciliado;
- `NO_TRADE`: sin señal, cero órdenes y razón observable;
- `STALE`: datos viejos, `stale_context`, cero órdenes;
- `KILL_SWITCH`: marker del operador, riesgo aprobado, **cero** llamadas al
  broker, rechazo `hot_stop`;
- `EXCEPTION`: proveedor que lanza, error registrado, cero órdenes.

### REQ-G5-05 — Sin live

No se construye ningún cliente de exchange, no se leen credenciales y no se
envía ninguna orden. El ledger de admisión usado en la evidencia es un fixture
`CONTROLLED_TEST_FIXTURE`, no una admisión de producción ni evidencia de edge.

### REQ-G5-06 — Verificación separada

Un script distinto debe exportar el commit con `git archive`, ejecutar la
evidencia dos veces y re-derivar cada criterio. El veredicto solo puede ser
`G5_VERIFIED` si todas las comprobaciones pasan.

## 5. Límites

- Los datos son sintéticos y la admisión es un fixture controlado: la
  evidencia demuestra **alcanzabilidad del recorrido**, no rentabilidad ni
  calidad de una estrategia.
- El reinicio es lógico (instancias nuevas, mismo proceso y mismo disco), no un
  `kill -9` del proceso. El estado se relee del fichero durable.
- El ledger de producción no admite estrategias, por lo que el comando de
  producción termina en `NO_TRADE`; no se modifica la política de admisión.
- No se contacta ningún exchange ni se usa ninguna credencial.
- `paper_cycle` y `autonomous.decision` siguen siendo dos motores; G-5 no los
  unifica.
- La verificación es `PROCEDURALLY_SEPARATED` (script distinto, mismo autor),
  no una segunda persona.
