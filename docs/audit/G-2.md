## 1. CLAIM

The kill switch is consulted only through the environment variable read **at
import time** (`KILL_SWITCH_ENV` → `_boot_kill_switch()`), and the process-wide
authority is constructed once. An operator who discovers a runaway loop has
exactly one lever: kill the process. That is a real defect: stopping the
process also drops the open paper positions' bookkeeping and loses the run's
evidence, and there is no way to engage the stop between two decisions of a
running cycle.

**G-2 closes that gap**: a running process can move to `ENGAGED` without a
restart, and the move takes effect before the next broker call.

## 4. DECISION

### 4.1 Channel: a control file, not a new network surface

Reuse the convention that already exists (E-7): an operator writes
`<run_dir>/KILL_SWITCH`; the live process polls it. No HTTP endpoint, no socket,
no dependency, no authentication to invent. The authorisation boundary is the
filesystem permission on `run_dir`, which is the same boundary `STOP` already
relies on — and `STOP` is documented, not weakened, by this contract.

The CLI gets the real subcommand that `app.py` reserved for exactly this
(`kill-switch --run-dir … --engage`). `status` stays a stub.

### 4.2 Two layers, both fail-closed

1. **Rule 0 (existing).** `engage` activates the process-wide `KillSwitch`
   (`HALTED`), so every subsequent `intend`/`decide` returns `NO_TRADE` before
   reading the packet.
2. **Dispatch boundary (new).** A lock-guarded check at the last point before
   `broker.execute_signal`, independent of rule 0. A future regression that
   bypasses the decision engine still cannot send.

Neither layer can be argued with by risk, verifier, agent or LLM.

### 4.3 Linearization (REQ-G2-03)

`HotStopGate.order_boundary()` is a context manager that **holds the same lock**
as `engage()` for the whole broker call:

- `engage()` returns its ACK only after acquiring that lock, so it cannot
  return while a dispatch is in flight;
- therefore **no broker call can begin after the ACK**, and every call that
  began before it has finished by the time it returns.

This is stronger than the handoff's minimum (it also forbids the "began
earlier, finishes after ACK" window), and it costs one lock hold per order.
The trade-off is explicit: `engage` may block for the duration of one broker
call, bounded by `boundary_timeout_seconds` (default 30 s). On timeout the gate
**engages anyway** and reports `LOCK_TIMEOUT`: a slow order must never delay a
stop.

### 4.4 Monotonicity (REQ-G2-02)

Engaged is terminal for the life of the process. There is no disarm path: the
gate exposes no `disengage`, deleting the control file does nothing, and the
CLI refuses to clear it. The only way back to trading is a new process with the
existing explicit off token (`KILL_SWITCH_ENV`), whose semantics are untouched.

### 4.5 Evidence (REQ-G2-06)

`<run_dir>/kill_switch_events.jsonl`, one JSON object per transition:
`event`, `run_id`, `previous_state`, `new_state`, `activated_at_ms`, `actor`,
`reason`, `commit`, `boundary`, `lock_timeout`, `orders_blocked`,
`broker_calls_allowed`. No credentials, no payloads, no proposal contents.

**Two ACKs, two meanings** — never merged:

| ACK | Meaning | Where |
|---|---|---|
| CLI exit 0 + `{"status":"REQUESTED"}` | the request is durably on disk | `trading-bot kill-switch --engage` |
| audit `event=engaged` | the **process** is engaged; no further broker call | the running loop |

Only the second is enforcement. The CLI's stdout says so.

## 6. Requirements

| ID | Requirement |
|---|---|
| REQ-G2-01 | **Hot engage.** An explicit authorised action moves a running process to `ENGAGED` without restart. The LLM/agents cannot engage or disarm. |
| REQ-G2-02 | **Monotonic.** Idempotent; no disarm and no rearm inside the process. Boot policy unchanged and untouched. |
| REQ-G2-03 | **Point of no return.** After the in-process ACK no new broker invocation can begin; in-flight ones are serialised by the lock. |
| REQ-G2-04 | **Independent of risk.** With the gate engaged, a `PASS` from the risk engine produces zero broker calls. |
| REQ-G2-05 | **Fail closed.** Unreadable/invalid control file, unreadable switch, lock timeout, audit failure ⇒ blocked, never allowed. |
| REQ-G2-06 | **Auditable.** Event record as in §4.5. |
| REQ-G2-07 | **No scope creep.** G-1 persistence, G-3 live, G-4 `paper_cycle`, merging to `main` and cancelling in-flight orders stay out. |
